# falsify-the-problem

[English](README.md) | 简体中文

> 尽早发现：你可能正在解决错误的问题。

一个轻量的 Agent Skill，在提出方案之前，先检验当前的问题定义。
它问的是：**我们正在解决的问题，真的对吗？**

| 使用前 | 使用后 |
| --- | --- |
| “API P99 从 300 ms 涨到 2.8 s，加 Redis 吧。” → 开始设计缓存 | 先核对延迟来自哪里，检验数据库耗时是否确实主导了尾延迟，再决定保留还是更换问题定义 |
| “留存低，加推送吧。” → 开始做提醒功能 | 先区分：用户体验到了价值却忘了回来，还是从来没有体验到价值 |

只需一个 Markdown 文件，无依赖、API Key、服务器或数据库。
它聚焦于可证伪的问题定义、有实质差异的替代定义、每轮一个主要区分性检验，
以及根据证据更新判断，并在设计方案之前明确交还控制权。`KEEP` 也是成功结果。

## 为什么需要它

用户提出的方案里，往往已经藏着一个未经检验的问题定义。
沿着这个方案不断优化，可能只会让错误方向上的投入越来越大。
这个 Skill 把隐含的问题定义摆出来，寻找成本低、足以推翻它的证据。
它适用于编码、调试、架构、研究和产品工作，在不同领域使用同一套检验流程。

## 工作流程

1. 保留观察及其来源，区分解释、因果假设、问题定义和拟议方案。
2. 找出当前的问题定义，以及合理且有实质差异的替代定义。
3. 找出支撑各定义的关键假设，推导出可以通过观察区分的预测。
4. **每轮选择一个主要区分性检验（Primary Discriminating Test）**，
   权衡信息价值、成本、风险和时间。对于可访问、已获授权且获取成本低的证据，直接检查。
5. 根据结果增强、削弱、否定或合并候选定义。如果下一项观察值得付出成本，继续调查。
6. 给出总体结论，结束本轮检验，把控制权交回宿主 Agent。

选择主要区分性检验之前，Skill 会检查所有现有候选是否共享同一个重要但未经验证的前提。
必要时最多补充一个有依据的框架外候选；无法解释的新证据也可以重新触发这项检查。
输出默认按 Fast / Normal / Deep 三档保持简洁，后续轮次只展示变化的证据和判断。

| 总体结论 | 含义 | 如何交接 |
| --- | --- | --- |
| KEEP | 当前定义已经得到充分验证，且获得最多支持 | 求解 ALLOWED；宿主继续已获授权的工作 |
| WEAKEN | 当前定义失去了重要支持，但仍有可能成立 | NOT YET；继续调查剩余的不确定性 |
| KILL | 原定义已无法成立，尚未确立替代定义 | 基于该前提的求解 BLOCKED |
| REFORMULATE | 一个有实质差异的替代定义已获得充分支持 | NOT YET；明确返回重构后的问题（Reformulated Problem），交给后续环节验证 |
| INSUFFICIENT EVIDENCE | 现有证据不足以区分候选定义 | NOT YET；继续调查，或索取最少的必要缺失证据 |

`BYPASS` 表示是否启用 Skill 的决定，不属于总体结论。`KILL` 不意味着已经找到了替代定义。
在 `REFORMULATE` 之后，宿主可以利用已有证据，简短地再验证一次新定义，
获得 `KEEP` 后继续任务范围内的工作。

**停止求解，不等于停止调查。Skill 结束，不等于宿主 Agent 停工。**
获得 `KEEP` 后，已经得到实施授权的宿主可以在同一轮继续完成任务，无需再次请求许可。
这个结论本身不会授予新的权限。

## 一个例子

用户：“API P99 从 300 ms 涨到 2.8 s，加 Redis 吧。”

- **观察：** 用户报告的（`user-reported`）延迟上升，尚未独立验证。
- **解释：** 数据库慢。**因果假设：** 重复读取拖慢了请求。
  **方案：** Redis。这些都是推断，不是已经测量确认的事实。
- **当前问题定义：** 数据库处理耗时是尾部慢请求延迟的主要组成部分。
- **替代定义：** 排队或容量不足、下游依赖延迟、测量偏差。
  如果证据指向运行时暂停或负载构成变化，也应将其纳入考虑。
- **关键假设：** 慢请求确实把大量时间花在了数据库操作上。
- **主要区分性检验：** 检查同一时间窗口内可获取且有代表性的慢请求和普通请求样本，
  在一次对比中核对端到端延迟与排队、数据库、下游耗时。
- **结果如何影响判断：** 数据库耗时升高会增强当前定义；数据库耗时稳定而排队时间上升，
  会削弱当前定义并支持容量问题；各项耗时与总耗时对不上，则支持测量问题。
  链路片段稀疏或重叠时，仍需保留不确定性。

如果尚未检查证据：结论是 `INSUFFICIENT EVIDENCE`，求解状态为 `NOT YET`。
证据可访问时，宿主应继续检查。如果可靠的观察确立了排队等待才是主要延迟来源，
则给出 `REFORMULATE`，明确新的问题定义。这两种结果都不会自动授权实施 Redis 方案。
这只是用于说明流程的例子，并非真实生产事故报告。

## 什么时候用

想要挑战当前的问题定义时，可以显式调用。
自动启用则需要**同时满足：问题定义存在实质不确定性，且干预成本或风险不可忽略**。
典型信号包括：

- 问题还没经过检验，方案就已经确定了。
- 把因果假设当成已经观察到的事实。
- 调试或研究反复失败，却始终沿用同一个问题定义。
- 还没完成诊断，就开始技术选型或代价较大的产品改动。

## 什么时候不用

对于已验证的诊断、明显的编译错误、错别字、格式调整、翻译、机械性编辑，
以及成本很低且可逆的改动，通常不应自动启用。
不要仅仅因为逻辑上存在其他可能，就凭空制造不确定性。

例如，编译器报告找不到 `UserService`，检查仓库后确认它已被重命名为 `AccountService`。
“修正 import”通常应直接跳过这个 Skill。
如果用户显式调用，简短给出 `KEEP` 后，就让宿主继续修复。

## 与其他方法有什么不同

**这些方法彼此有重叠。本项目只聚焦一项范围更窄的操作职责。**

| 相关方法 | 重叠之处与侧重点差异 |
| --- | --- |
| problem-framing | 通常追求更清晰、更有用或范围更合适的问题定义。本 Skill 把当前定义视为可证伪的假设，寻找反证，通过区分性检验更新判断，并明确停止条件。其他问题定义方法也会挑战假设。 |
| debugging | 通常追问故障由什么引起。本 Skill 先问：为什么把故障归为这一类问题？之后可以继续根因调查，但列出多个可能原因，并不等于提出了有实质差异的问题定义。 |
| grill-me | 挑战计划、设计或提案。本 Skill 在形成计划之前，先挑战问题定义。 |
| critical-thinking | 是范围更广的推理工具箱。本 Skill 只负责一件事：在求解前，验证、削弱、否定或替换当前的问题定义。 |

区别在于侧重点、操作流程、证据更新方式和停止条件。
本项目不声称发明了“重新定义问题”这件事。

## 安装

完整的运行时指令只有 [SKILL.md](SKILL.md)。仓库是它的分发目录，
评测文件属于开发材料，不是运行依赖。

1. 下载或克隆仓库到本地的 `falsify-the-problem` 文件夹。
2. 如果宿主支持 Skill 文件夹，将包含 `SKILL.md` 的文件夹放入该宿主文档指定的位置，
   按其正常流程重新加载或发现 Skill。也可以只把 `SKILL.md` 复制到同名文件夹中。
3. 如果宿主支持可复用的 Markdown 指令，附加或加载完整的 `SKILL.md`，
   并在求解任务之前显式要求使用它。

无需安装软件包或启动服务。存放路径、发现机制、调用语法和工具权限取决于具体宿主。
设计上，它可以用于支持可复用 Markdown 指令或类似 Skill 工作流的 Agent；
但尚不能保证不同宿主上的行为一致。

## 使用方式

```text
解决下面的问题前，先使用 falsify-the-problem：
我们的 API P99 从 300 ms 涨到了 2.8 s，觉得加 Redis 就能解决。
先检查本地可获取的证据，挑战这个问题定义。
```

```text
使用 falsify-the-problem：
留存低，我们想加推送通知。
什么低成本观察能区分“用户忘了回来”和“用户从没体验到价值”？
```

```text
使用 falsify-the-problem，如果问题定义经得住检验，就完成已授权的修复：
编译错误和仓库中的重命名记录都表明 import 已经过时。
修正这个 import。
```

Skill 负责问题定义的检验；宿主负责工具、访问、权限和后续实施。
对求解设置门槛，不能变成拒绝检查证据，也不能变成获得 `KEEP` 后仍然停工。

## 评测

参见[评测说明](evals/README.md)、[20 个案例](evals/cases.md)和[评分标准](evals/rubric.md)。
案例覆盖上述五个领域、多轮证据矛盾、证据不可获取、可直接访问的材料，以及不应启用 Skill 的负对照。
评测关注推理行为，不要求复现固定措辞。

[冒烟测试记录](evals/smoke-tests.md)包含执行上下文、输出、分数、审查发现和修订。
**这是行为冒烟测试，不是具有统计效力的基准测试。**
小规模开发测试无法证明普遍有效，也无法证明行为不受宿主影响。
必须明确说明基线的来源，以及哪些执行没有实际发生；反事实分析不能当作模型输出。

[全量案例后续评测](evals/full-suite.md)记录了 20 个配对案例、隐藏实验组标签的独立评分，
以及基于 Skill 目录的启用探测。部分变体提供的是报告，而非底层原始系统。
虽然评分者看不到组别标签，流程措辞仍可能暴露是否使用了 Skill。
记录保留了原始分数、作者与评分者的分歧、实际完成的本地修复，以及回答长度成本。
这些结果尚未证明跨模型或跨宿主的有效性。

[R03 数据材料后续评测](evals/r03-raw.md)使用预先构造的合成逐条预测数据，
检验是否选择并执行“站点 × 预处理”的对比，并区分目标站点错误率下降与站点间差距缩小。
这些人为构造的输出不代表实际运行过分类器。
在这一单独变体中，两组均为 10/10，不能据此证明 Skill 有优势。
记录保留了标签审计和评分范围方面的限定说明。

[R03 配对缺失测试](evals/r03-stress.md)移除了最初的重放提示，
加入表现退步的样本和配对覆盖不完整的情况，检验 Agent 能否区分“匹配子集的结果”
与“全部选定记录仍未确定的结果”。两组再次均为 10/10；
记录保留了对首次检验如何标注的歧义，以及采用更严格解释时的备选评分。
这仍然只是单个由作者构造的配对评测。

[更难的问题定义评测](evals/hard-suite.md)新增 12 个案例，覆盖部分成立的解释、共享盲点、
目标错位、混杂检验和证据反转，并包含两个已验证诊断的负对照。
[覆盖检查微型评测](evals/coverage-eval.md)另有跨五个领域的六个定向案例。
这些开发记录分别报告质量、失败类型和可见回答长度；此前的评测仍是历史快照，
不代表修订后 Skill 的测试结果。

本次预先归为 Normal 的九个 harder cases，整例累计可见词数中位数为：旧版 Skill 218、
新版 178、原生 baseline 117。六个定向覆盖案例两组均为 10/10，
R03 首轮仍遗漏输入处理路径。这支持本轮可见输出缩短的结论，
尚不能证明普遍的覆盖改善或相对原生模型的优势。

## 设计原则

- 一个职责，一套跨领域流程，一个可移植的指令文件。
- 保留证据来源；报告不等于独立验证。
- 优先提出有实质差异的问题定义，避免只给同一种原因换个说法。
- 选择那些不同结果会改变决策的检验。
- 允许证据推翻先前结论，让调查投入与问题相称。
- 将 `KEEP` 和及时交给后续环节视为正常的成功结果。

## 局限

Markdown 指令只能引导宿主，不能强制执行运行时门槛。
证据质量、访问条件、模型判断，以及是否选择启用 Skill，都会影响结果。
检验可能无法得出结论，也可能支持多种原因共同作用，或者只足以支持有限范围内的判断。
这个 Skill 不能证明已正确识别因果关系，不能保证替代定义正确，也不能代替专业审查。
它不是评测运行框架、运行时、通用调试框架、多 Agent 系统、编排引擎、记忆系统或 AI 科学家。
